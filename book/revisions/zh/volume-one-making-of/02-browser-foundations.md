# 页面出现之前，浏览器在忙什么？

上一章，我们从课程页面一路看到了服务和数据库。这一章先把镜头拉回来，看看浏览器怎样把收到的东西变成眼前的页面。页面出现之后，事情也没结束。标题能看见，搜索框能输入，搜索结果却迟迟不变，这同样是浏览器里需要解释的问题。

我们继续使用那个虚构课程网站。把页面缩小到一个标题、一个搜索框和一个按钮，分别看看它们在等什么。

## 同样是“慢”，等的可能不是一件事

设想你打开课程列表，页面还没有显示标题。你说：“这个网站有点慢。”另一次，标题和搜索框已经出现，你输入关键词，搜索按钮却还不能用。再过一会儿，按钮可以按了，但按下后很久才有反馈。

从用户这边看，都是等待。从实现这边看，至少有几件不同的事值得问：内容是否已经到达？浏览器是否能把它画出来？搜索行为是否已经准备好？负责处理这次操作的代码，是否有机会执行？这些问题也可能同时发生。不能凭一张空白截图，就断定后端慢；也不能因为按钮已经画出来，就宣布搜索功能已经准备完毕。

为了把事情说具体，我们给这个例子定几个条件：页面最初的 HTML 里已经有标题、搜索输入框和几张课程卡片；页面头部引用一份外部样式表；另有一段 JavaScript 负责接管搜索。搜索按钮使用 `type="button"`，开始时处于禁用状态，脚本成功安装处理逻辑后才启用它。

“开始时禁用”是我们为这个例子选择的产品行为，方便用户看出它还没准备好。它不代表所有网站、所有按钮都必须如此设计。接下来，我们就沿着这一个页面，看看它在等什么。

## 文件到了，还要变成可操作的文档

浏览器收到 HTML 时，收到的是文本。它需要识别其中的元素和关系，把它们组织成一份文档。例如，下面只是页面结构的一小段，不是完整可运行的搜索程序：

```html
<h1>找到下一门课程</h1>
<label for="query">课程关键词</label>
<input id="query" type="search">
<button id="search" type="button" disabled>搜索</button>
<section class="course-card">浏览器基础</section>
```

这段结构表达了标题、输入框、按钮和课程卡片。`label` 通过 `for` 与输入框关联；`disabled` 则让按钮暂时不可操作。它们已经带有浏览器认识的语义，不是几块等待 JavaScript 来赋予一切能力的色块。

解析之后，页面中会有相应的节点：标题节点、输入框节点、按钮节点，以及它们所在的文档关系。程序可以查找、读取或改变这些节点。这份可操作的文档表示叫 [DOM，Document Object Model](https://html.spec.whatwg.org/multipage/parsing.html#overview-of-the-parsing-model)。例如，替换课程标题的文字，就是在改变其中的一个节点。

CSS 再为这些元素提供视觉规则：标题多大，卡片多宽，输入框与按钮之间留多少距离。浏览器把样式规则组织成可处理的表示，通常称为 **CSSOM**。这样，文档里的课程卡片就有了可供匹配的外观规则。

JavaScript 可以在这份文档上安装行为。例如，找到搜索按钮，为它登记一个点击时要执行的函数，再在收到结果后替换课程列表。登记这样的函数，通常叫安装事件监听器。

HTML 自己也有行为。普通链接可以导航，输入框通常可以接收输入，表单也可以按 HTML 的约定提交。本例中的输入框可以先接收关键词；搜索按钮暂时不能用，是因为它被禁用，且我们选择用脚本实现搜索。页面上的交互不必在同一个时刻一起“开机”。

HTML 是输入，DOM 是浏览器构建、代码可以继续改变的文档。标题节点已经有了，接下来还要确定它会以多大的字、放在屏幕哪里。

## 不用等齐所有文件，有些依赖却绕不过去

浏览器通常可以边接收 HTML，边解析已经收到的部分。遇到外部样式表、脚本等引用时，也会发现需要获取的资源。它不必等网站的全部图片、全部文件都齐了，才第一次显示内容。

不过，哪些东西还没到，会影响眼前能做什么。

先看样式表。假设页面头部的样式表已启用，也适用于当前屏幕；浏览器需要它来确定页面的初始外观。在它尚未获取和处理好时，初次显示内容可能仍要等待。这是**阻塞渲染**的一类依赖。

等待样式的这段时间里，浏览器仍可以继续解析 HTML，其他工作也未必停下。如果这份样式表只用于打印，当前又是屏幕显示，情况就不同。因此，要问的是“当前显示依赖哪份样式”，而不是“是不是所有 CSS 都会让整个浏览器停下”。[web.dev 的关键路径说明](https://web.dev/learn/performance/understanding-the-critical-path#render-blocking-resources)区分了这两类依赖。

脚本带来的等待又有所不同。有些脚本执行时会改变文档，解析器需要先处理它，才能继续往后走。对于**解析初始 HTML 时遇到的外部经典脚本**，可以先看这个小比较：

| 写法 | 获取脚本时 | 执行与 HTML 解析的关系 |
| --- | --- | --- |
| 不加 `async` 或 `defer` | 解析器要等待获取与执行 | 这段处理完成后，才继续后面的解析 |
| 加 `defer` | 可以与解析重叠 | 文档解析完成后执行；多个此类脚本按文档顺序执行 |
| 加 `async` | 可以与解析重叠 | 脚本可用时尽快执行，可能打断尚未完成的解析；多个此类脚本不靠文档顺序保证执行先后 |

这里的“可以与解析重叠”说的是资源获取，不是脚本执行自动搬去了另一个 JavaScript 线程。模块脚本、动态插入的脚本还有各自的规则，不在这张表的范围里。[WHATWG 的脚本说明](https://html.spec.whatwg.org/multipage/scripting.html#the-script-element)给出了这些模式的区别。放回搜索例子：如果脚本要先找到文档中的搜索按钮，执行时机就影响它能不能找到。若它又依赖另一段脚本先准备的函数，两者的执行顺序也重要。直接给所有脚本加上 `async`，可能把原来的等待换成依赖错误。

解析暂停也不等于所有下载暂停。浏览器还可能提前扫描后面的资源引用，尝试继续获取资源。另外，样式表也可能通过脚本的执行条件，间接影响解析推进。这些依赖可能相互影响，需要分清它们怎样作用于当前页面。回到最初的两种等待：头部适用样式尚未就绪，可以让内容显示继续等；搜索脚本迟到或执行失败，则可能让标题和输入框已经出现，而这个增强搜索按钮仍处于禁用状态。它们值得分别检查。

## 从“有这个标题”到“标题在这里”

假设必要样式已经可用。浏览器还要把文档与规则结合起来，确定具体的视觉结果。

它先判断哪些样式适用于标题，算出字体、颜色等值，这部分工作通常叫**样式计算**。然后，要确定标题占多宽、多高，卡片从哪里开始，下面的内容放在哪里。这是**布局，Layout**。

几何位置确定之后，还需要把文字、背景和边框等视觉内容绘制出来。这部分工作称为**绘制，Paint**。再将视觉内容组合成可呈现的画面，就是**合成，Compositing**。对于这张课程卡片，浏览器既要知道标题占在哪里，也要把相应文字和卡片背景呈现出来。

### 标题怎样出现在屏幕上

可以用一张依赖图把这些关系接起来：

```text
HTML → DOM ──────┐
                 ├→ 计算适用样式
CSS → 样式规则 ──┘         ↓
                       确定几何位置
                           ↓
                       绘制视觉内容
                           ↓
                      合成与呈现画面
```

箭头表示这些工作的依赖，不是固定的线程分工；DOM 节点与布局盒子也不是一一对应的。顺着标题看，它先有文档中的内容和关系，再结合样式确定尺寸与位置，经过绘制、合成，才成为眼前的标题。

这些工作也不会在每次变化时完整重做。还是那张课程卡片，如果只改变文字颜色，文字的尺寸和位置可以不变，浏览器可以跳过重新布局。如果把卡片可用宽度缩小，长标题换成两行，卡片高度就可能改变，后面内容的位置也可能受到影响。这两种变化需要的[视觉更新工作](https://web.dev/articles/rendering-performance#the_pixel_pipeline)并不相同。

因此，“改了一个属性”没有固定的成本答案。要看它改变的是颜色、几何关系，还是别的条件，以及实际影响了哪些内容。也不必反过来认定，只要改了 DOM，就一定把整页重新布局、重新绘制一遍。

这还带来一个稍后会用到的区别：代码改好 DOM，说明文档状态变了；用户看见新画面，还需要相关视觉工作得到执行并呈现。两者不是同一个时刻。

## 按钮已经出现，谁来处理这一下？

回到搜索按钮。脚本成功找到它，安装了点击处理函数，然后将它启用。现在，这个特定的搜索行为才具备了我们约定的启动条件。

如果脚本获取失败，或者执行到一半抛出错误，标题可能照常显示，按钮却始终没有启用。此时要追的是安装条件和错误，不能只盯着搜索接口有没有变慢。

即便安装完成，也还有另一种等待：负责处理点击的执行环境正在忙。

对普通页面，可以先认识一个重要角色：**页面主线程**。页面的大部分 JavaScript 执行，以及许多文档解析、样式和布局工作，都需要它参与。持续占用它的同步计算，会推迟其他依赖它的工作，包括相应的事件处理。[web.dev 的任务与主线程解释](https://web.dev/articles/optimize-long-tasks#what_is_the_main_thread)讨论了这种关系。

设想我们在搜索已经能用之后，又让页面执行一段耗时的同步筛选。用户在这期间按下搜索按钮，监听器虽然已经安装，相关处理仍可能要等当前工作结束才能运行。画面可以继续保留先前的内容，看起来像“按钮没反应”。这与监听器根本没安装，是两种不同情况；也不能据此断言这次点击一定永久丢失。

## 请求在等，代码就一定不忙吗？

假设搜索终于开始处理了。我们想先显示“正在搜索”，再筛选课程，最后显示结果。把这段处理按执行顺序写下来：

```text
处理搜索点击：
  将反馈节点的文字改成“正在搜索”
  连续执行一段耗时的同步筛选
  将筛选结果写入列表
  将反馈节点的文字改成“搜索完成”
```

修改反馈文字的那一步，确实改变了 DOM 中的文档状态。但紧接着，同一段处理就开始持续计算。浏览器可能还没有机会呈现中间状态，反馈节点就又被改成了“搜索完成”。于是，程序走过了“正在搜索”，用户却未必看见它。

这不是在说中间文字永远不可能出现，而是在说，**一次 DOM 修改不承诺紧接着就有一帧把它显示出来。** 要解释具体页面，需要看实际执行和呈现记录。

浏览器会把需要调度的一段工作组织成**任务，Task**。处理一次输入事件可能启动一个任务，处理函数里又可以连续调用很多函数。函数调用不是每发生一次，就自动给画面更新插一个空档。参与选择和执行这些工作的机制叫**事件循环，Event Loop**。目前先抓住用途：事情发生了，需要安排相关工作执行；持续执行中的代码，会影响其他工作何时能轮到。具体调度涉及不同任务来源，不是一条可以随意推导所有先后顺序的绝对队列。

再换一种实现：页面发起真正的异步请求，并等待服务端返回。请求尚未完成时，等待它的函数可以暂停后续执行，页面主线程可以去做其他工作。请求等待，不要求这段函数一直占着 CPU。这里就能看见**异步**的用途：把“现在继续不了，要等结果”与“持续在执行计算”分开。

但给筛选函数加上 `async`，不会自动把同步筛选搬到另一个线程。`async` 函数在第一个 `await` 之前仍会同步执行；等待之后接着运行的普通计算，也不会因此自动并行。[MDN 的 async 函数说明](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function#description)给出了这个执行边界。先等一个请求、再用很久处理结果，仍然可能让页面在后半段迟迟不响应。资源返回得快，与处理结果的代码是否及时让出执行机会，是两个需要分别观察的问题。

下面只示意一种可能的关系，横向表示先后，不按时长比例绘制：

```text
资源：  发起请求 ── 等待结果 ── 返回
执行：  发起后暂停    做其他工作   → 后续处理 → 修改 DOM
画面：  旧画面 ─────────────────→ 在可呈现时更新
```

这三行是观察角度，不是三条固定线程。资源返回之后，相关后续代码还要得到执行机会；代码修改 DOM 之后，也仍要完成必要的视觉更新。图中的箭头更不保证反馈文字一定出现在下一次屏幕刷新中。

这里还有一层可选的解释：**微任务，Microtask**。Promise 的相关后续处理会使用微任务机制；在微任务检查点，待处理的微任务还会继续被处理。`await` 一个已经完成的 Promise，并不因此保证先显示一帧再继续。把 `await` 当作“现在立刻画一下”的指令，会误解它的职责。[HTML 的事件循环处理模型](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)把任务、微任务检查点与依条件安排的渲染工作分开描述。

这里谈到的页面主线程，只是浏览器工作的一部分。网络获取可以继续推进，一些已有画面的滚动也可能走合成路径。因此，能滚动并不能单独证明主线程空闲。另一种执行 JavaScript 的环境是 Web Worker，它可以承担某些工作，但不能直接操作这个页面的 DOM，需要通过消息等方式与页面协作。[Worker 的能力边界](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers#web_workers_api)值得知道；这里先不增加一个 Worker 实现。

回到眼前的搜索，我们可以先问清：我们在等待哪个结果，哪段代码还在连续工作，中间状态有没有得到呈现机会。具体要不要减少计算、拆分工作或移交给另一个执行环境，应根据这些依据再选。

## 下一步看什么，才不会靠猜？

现在可以把最初的“有点慢”，换成更具体的假设。

| 眼前需要解释的情况 | 可以提出的假设 | 下一步找什么依据 |
| --- | --- | --- |
| 标题还没有显示 | HTML 或当前显示需要的资源尚未就绪，也可能已有执行或视觉工作在等待 | Network 中的资源状态、请求先后与依赖；必要时对齐 Performance 的加载记录 |
| 标题可见，增强搜索按钮仍禁用 | 脚本未到、执行失败，或安装条件尚未满足 | 脚本请求、Console 错误、安装处理逻辑与启用按钮的实际条件 |
| 按钮已启用，处理或反馈迟到 | 主线程持续忙，或处理已经开始但在等其他结果 | 输入与处理的先后、Performance 主线程工作、相关请求，以及反馈状态的变化 |

这张表不是互斥的故障分类。一个脚本可以先获取得慢，运行时又做太多计算；界面也可能因为业务条件主动禁用按钮。假设的价值，是帮我们选择下一条证据，而不是提前宣布根因。

例如，先在 Chrome DevTools 的 **Network** 面板里看搜索脚本是否还在等待，或搜索请求是否已经发出。接着查看请求的 [Timing 分解](https://developer.chrome.com/docs/devtools/network/reference#timing-explanation)：等待首字节包含网络往返与服务端准备响应的时间，不能直接当作后端代码耗时；读取响应体的时间也可能受浏览器忙于其他工作的影响。

如果脚本已到、按钮也已启用，就可以在 **Performance** 面板中[记录这次搜索交互](https://developer.chrome.com/docs/devtools/performance/overview#capture-and-analyze-a-performance-report)，对齐输入、主线程活动与视觉更新：反馈迟到，是前面有工作占着主线程，处理函数还没开始，还是处理已经开始、正在等请求结果？再结合 Console 的错误和按钮启用条件，把假设逐个缩小。

再想一个小问题：搜索框看得见，脚本请求也返回了 `200`，为什么仍然不能证明搜索能用？

因为请求状态只回答了其中一层。脚本可能还没有完成执行，可能在安装监听器前报错；即便监听器存在，处理也可能被其他工作推迟。还要检查按钮的准备条件，并真正观察搜索行为及其结果。页面可见、资源收到、代码执行与特定操作可用，是有关联的几件事。

有时你还会看到 `DOMContentLoaded`。它表示 HTML 已解析完成，相关延后执行的脚本也已完成；它并不等所有图片或 `async` 脚本，更不会替产品检查搜索是否真的可用。样式表还可能通过脚本等待关系影响这个事件的时机。[MDN 的事件说明](https://developer.mozilla.org/en-US/docs/Web/API/Document/DOMContentLoaded_event)解释了这些条件。加载里程碑可以提供线索，功能准备好仍要看这个功能自己的条件。

如果请 AI 帮忙分析，可以提供这些具体信息：看不见的是什么，哪次操作没有反馈，哪些资源已到，是否有错误，哪段执行记录值得看。我们可以请它据此整理可能的原因，解释资源、执行与画面之间的依赖，再对照这个页面的实际条件核对。这样，讨论就有了具体对象；如果建议是“把脚本改成异步”，仍需要检查依赖、执行与实际行为。

先前那次搜索，标题出来了、按钮亮了、请求发出去了，现在你知道在哪里能看见这三步。等老师要学员提前读一份讲义，问题就越出了这个窗口：老师合上电脑以后，究竟还有谁在替她办事？

- [WHATWG：script 元素](https://html.spec.whatwg.org/multipage/scripting.html#the-script-element)：声明式行为、外部经典脚本模式及其范围。
- [web.dev：关键渲染路径](https://web.dev/learn/performance/understanding-the-critical-path#render-blocking-resources)：渐进处理、渲染依赖与解析依赖。
- [web.dev：渲染性能与像素流水线](https://web.dev/articles/rendering-performance#the_pixel_pipeline)：样式、布局、绘制和合成的概念模型；不同变化可能跳过部分工作。
- [web.dev：任务与主线程](https://web.dev/articles/optimize-long-tasks#what_is_the_main_thread)：持续占用主线程的工作，怎样推迟接下来的交互处理。
- [MDN：DOMContentLoaded](https://developer.mozilla.org/en-US/docs/Web/API/Document/DOMContentLoaded_event)：解析和脚本里程碑的条件，不代表完整产品就绪。
- [MDN：async function](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/async_function#description)：同步执行、等待与后续处理。
- [WHATWG：事件循环处理模型](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)：任务、微任务检查点和渲染条件；不作为固定帧序列图使用。
- [MDN：使用 Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers#web_workers_api)：独立执行环境与不能直接访问页面 DOM 的边界。
- [Chrome DevTools：Network 时间分解](https://developer.chrome.com/docs/devtools/network/reference#timing-explanation)与 [Performance 记录](https://developer.chrome.com/docs/devtools/performance/overview#capture-and-analyze-a-performance-report)：观察入口与计时解释，具体界面随版本变化。
