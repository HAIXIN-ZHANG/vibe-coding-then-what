# 同一份程序，搬家以后少了什么？

你在电脑上把一份讲义转成了六张预览图。换到部署环境，再传一次，照样有六张。隔天重启工作进程，数据库还郑重其事地列着六个地址，点进去却一张也找不到。程序大约没有忘记算术。先看看它昨天把图放在哪儿了。

在本机，临时目录有时比它的名字更长寿。跑在可替换容器或短时函数里的进程，重启、迁移或扩出新实例之后，却未必能看见先前实例的本地文件。容器镜像可以带上运行时和转换工具，镜像启动后写进去的数据还得另约保存地点。讲义和发布的预览可放在受控的持久存储里；临时工作区可以丢，只要有原件、任务记录和足够的信息重新生成。别把“昨天碰巧还在”写进产品承诺。

## 出门前带齐了什么

先核对部署的制品。依赖清单说允许哪些版本，锁文件帮助确定具体解析结果；构建还可能依赖操作系统、CPU 架构、字体和本机工具。一个只在你电脑上装过的 PDF 转换器，并不会因为同事把 JavaScript 依赖锁得很认真就出现在服务器上。固定并记录构建输入，给生成的制品标识；把验证过的同一份制品带进下一环境，配置和权限按环境提供。

观察可以从小处开始。进程是不是刚启动就退出？日志里有没有“找不到命令”或缺少配置？健康检查请求的是实际监听的端口吗？在本机访问 `127.0.0.1` 成功，只说明这个进程所在的网络环境能到达它的回环地址。换到另一个容器，那个地址指的是另一个家。一个公开的健康端点返回正常，也只证明它检查过的事情。试着让工作进程用自己的身份读一份获准的测试原件，写预览，再用正常的授权路径取回，才能回答老师的那个问题。

有些配置只是端口和日志级别，有些则是能够读取私有讲义的凭证。后者用受控的密钥配置或工作负载身份交给需要它的进程，只赋予相应存储范围和动作。出错时记录缺的是哪项能力，别把凭证的值贴进日志。以后轮换密钥，旧实例是否仍在使用旧值、新实例是否能启动，都值得纳入交付检查。

## 给谁租多大的房间

短小的查询接口可能很适合按需启动、自动伸缩的函数。要确认冷启动是否影响学员等待、并发上限和下游连接是否协调、执行时间限制能不能容下这段工作。随时到来的长时间讲义转换更适合可持续领取任务的工人，或者能持久记录、分段运行的托管任务服务。容器可以跑在长期服务里，也能被平台临时启动；“用了容器”和“工作能活多久”是两个问题。长期实例空闲时也占资源，按调用伸缩则可能把排队突然转移到数据库，费用和维护责任要按实际工作形状估。

例如用 AWS Lambda 处理一页缩略图，把原件版本和页码当作同一项工作的标识，重复收到事件也只发布这项工作的有效结果。整本转换若难以在一次执行中完成，又必须在中断后接着做，就让有持久任务记录和检查点的工人接手。[AWS Lambda 的重复事件处理建议](https://docs.aws.amazon.com/lambda/latest/dg/best-practices.html)

学员访问的是公开域名和 HTTPS 入口，入口再把课程请求送往应用。工作进程与文档存储可以只在受限的网络路径上相通。入站规则决定谁能发起连接，出站路径会影响进程能不能找到存储或转换服务。连得上以后，服务身份、资源权限和本次学员的业务授权，还要各自成立。开发者若只听见一句“没权限”，便可能忙着调整网络；若用权限更大的个人身份试成功，也还不能证明工人自己的钥匙能开门。

最小的一次搬家验收，其实还是那几张图。给测试讲义一个确知的版本，记下任务号，等工人写完，把服务重启，再从授权入口打开相应预览。若此时仍能看见第六页，你获得了一条很具体的证据。这比在群里回复一句“容器是绿的”要长一点，老师却看得懂。
