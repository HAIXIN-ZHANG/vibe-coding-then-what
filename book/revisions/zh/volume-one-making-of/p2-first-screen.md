# 课程介绍已经出来了，“我的报名”还在等谁？

你把课程链接发给朋友。他打开就看见周末有一场摄影课，给你回了个“不错”。你这边打开“我的报名”，屏幕上那个小圈还在转。明明是同一个网站，难道你俩连的是两种网？

不妨先看清两个页面各要交出什么。公开介绍可以让大家读同一份。个人名单得知道你是谁，查到你获准看的记录，才能填上名字。两边都可能慢，却有不同的机会让人少等一程。

## 谁先把字写进 HTML

第一种做法是提前做好介绍页。发布课程时就写好 HTML，请求来了，直接发那一份。这叫静态生成。标题会跟着第一份文档到达，对一段能直接读的课程介绍很合适。代价也在这里：老师把周六改到周日，得让新版本及时生成、替换旧副本，再看看缓存里还留了什么。随时会变的名额不宜悄悄写成页面上的永久保证。

个人页可以在请求到达后由服务端查记录、生成 HTML 再送来，这叫服务端渲染。学员收到的文档可以已经列着自己的课程，但第一批有用的字也可能在等那次查询；带个人名单的响应不能交给另一位学员共用。还可以先发一个页面骨架，让浏览器收到脚本以后自己去请求名单，然后把结果填进去。这种客户端渲染给后续筛选留了方便，第一次打开则可能多走“收到文档、获取并执行脚本、才开始查名单”这一串依赖。

这些办法能搭在一起。服务端先写出可读内容，浏览器再把事件和状态接到现有结构上，常叫 hydration。标题已经出现，不等于“筛选”已经接好。普通链接如果本来就指向有效页面，脚本还没准备好也可以导航。想起前面那个等待监听器的搜索按钮，就能知道该分别试哪两件事。

## 一次少等在哪里

假设个人名单要同时显示课程标题和报名状态，背后恰好由两个已有服务提供。可以让浏览器各问一次，也可以让面向这个页面的后端替它收齐，常叫 BFF。若两个查询彼此独立，后端可以并行请求，按同一身份筛选，再把页面需要的形状送回来。这样省去的是浏览器协调两份回复的负担。慢服务依然要花那些时间；聚合层自己也会失败，尤其要约定缺少一份时还能显示什么。用不用这一层，和 HTML 在哪儿生成，是两次不同的决定。

想比较两种页面，先在纸上写三个可以观察的时刻：看到标题、能用键盘打开详情、名单显示本人的报名。然后在相近的设备和网络条件下分别看首次进入与再次进入。文档很快到但标题晚，可以查必需样式或阻塞工作；标题已到但交互晚，就去看脚本下载、执行和接管。若名单请求早就开始，时间大头花在等它回复，再把图片压小一半，可能只会得到一张更小的图片。

图片仍然值得管。把一张供打印的大海报当卡片缩略图下载，学员已经替那些看不见的像素付了传输时间。给设备合适的资源和预留尺寸，可以分别减少字节与布局跳动。先定一个与目标设备、网络和任务相关的资源预算，再用实际传输大小、长任务和布局变化核对，数字才有出处。这里是一个选检查对象的例子，还没有谁拿秒表量过这个虚构的网站。

## 两个人把手机换一换

你可以在纸上先做一次很省钱的页面实验。开两个窗口，甲已经报了摄影，乙只是来看看。两人打开完全一样的公开课程地址，看到同一个标题很合理。此时把带名字的一小格也放进这份大家共用的 HTML，写上“甲，你已报名”。甲第一次看会很满意，满意得几乎想不到顺手把这个链接发给乙试试。

于是把私有那格移出来，等身份核实后再请求。公开内容可以继续分享；甲看得到自己的名字，乙应看见适合自己的报名入口。已经登录的人请求身份接口也会失败。此时告诉乙“暂时查不到你的报名”，比默认渲染一个可以再报的按钮可靠。不能因为要保持卡片高度稳定，就先猜一个好摆的业务状态。

换到甲这边，他想先看看讲义再出门。若渲染个人区的程序规定，头像、课程介绍、报名记录和六张讲义预览全部齐了才能显示，他明明已经报好名，却要为尚未生成的第六页等上一阵。把“我的场次”和“讲义预览”分开：一边显示已查明的周六上午十点，另一边显示原件已收、预览在做。这样做多了两种分别失败、分别重试的状态；它的回报是，即使预览工人今天告假，甲也不至于连几点出门都不知道。

还有一个比较办法。给首次到访、刚刚返回、刚从账号甲切换到乙三种情况各开一次页面。第一次慢，常要看要下载哪些东西；第二次仍显示旧场次，要看已有副本用什么条件更新；第三次最要紧的是清掉或重核上一位可看的个人记录。它们看起来都是“进入课程页”，得拿不同的结果来验。页面骨架先到，也许三次都很快。如果报告只记骨架出现的那一下，交给老师看时，大概还得请她自己去找名单代理出席。

现在回到朋友发来的“不错”。你可以继续追他的介绍标题怎样到得那么早，也可以点开自己的那次名单请求。下一部分就沿着后一条路走。浏览器说“请求已经发出”时，这条消息离那个能回答你的人，还有多远？
