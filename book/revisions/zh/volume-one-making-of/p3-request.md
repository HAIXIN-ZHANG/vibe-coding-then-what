# 请求出门以后，谁签收了它？

点下搜索，浏览器的网络面板多出一行。你把手指放到这行最右边，那里写着一段等待时间。做服务端的朋友恰好坐在旁边。他还没来得及打开日志，脸上已经有了被点名回答问题的神情。

假设学员第一次访问我们的课程站，浏览器手头还没有可复用的连接。它先要从域名得到可连接的地址；DNS 的结果可能有缓存。然后建立连接，在 HTTPS 下协商加密并检查对方的证书。到了可以交换 HTTP 消息的时候，页面才有机会提出“找标题含 HTTP 的入门课”这个具体请求。再次搜索若能沿用连接，前面这几步未必重走。你在面板里看到的一整段时间，不能全记在写查询的朋友头上。

## 门口收到，和教室收到

请求到了站点入口，接住它的可能是代理或负载均衡器。它依据主机名和路径等规则选应用。应用看明白查询条件，去数据源找课程，整理成回复，再从入口送回浏览器。每一步都可以留下不同的证据。域名解析失败时，应用日志通常连这位访客都认不出来；入口找不到健康的上游时，它可能自己回了错误；应用有一条“已收到”的日志，也只说明请求到了那一层。

比如浏览器报超时，应用却记着这次搜索在稍后完成。两句可以同时为真。沿同一请求标识核对开始和结束位置，才有机会解释中间花了什么时间。你若只拿到浏览器这一端，能说的是“在约定的等待时间内没取得结果”。把鼠标停在那行数字上，它没法替你去机房问话。

普通搜索适合学员问一次、服务答一次。讲义转换可能要等得久些，让页面隔一会儿带任务编号来查，简单，也会产生几次“还没好”的请求。若同一页面需要持续收到进度，服务端推送事件（SSE）可以沿一条连接往浏览器送更新；两边都需要频繁独立发消息时，还可考虑 WebSocket。外部转换商没有开着我们的网站，它办完后向我们的接收端发一笔通知，才是 webhook 那种走法。选哪条路，先看谁有新消息、谁能主动找谁，再算维持连接、断线重连和补漏的代价。

## 两张长得一样的收条

在纸上把刚才的搜索重做一次。小林输入“摄影”，入口记下请求 41，应用也记下 41。应用返回两门课，入口把这份回复送回，浏览器拿到后在页面上画两张卡。先别急着给这条线画满绿色的勾。把这几份记录分别交给三位同事，让他们只凭自己手里的那一份说一句话。

网关同事说：“41 进来过，我找到了一个能接它的应用。”他说的可以完全属实，哪怕应用接下来因为读不到目录而回错。做目录的人说：“我替 41 找到了两条记录。”他也没法担保回到小林手里的两张卡都有字。最后浏览器同事说：“这一页收到了回复。”收到一份响应和收到符合约定的课程资料，中间还差一层检查。若前端拿 `name` 当课名、后端送的是 `title`，这三个同事都可以交出自己的收条，小林却只能在两张空椅子之间挑一把。

再把 41 换成两个很像的请求。小林刚输完“摄影”，发现忘了限定周末，又搜了一遍。第一次请求慢，第二次快。老师说十点半确实有人查到两门课，我们怎样知道他说的是小林此刻等的那一笔？若只有“关键词等于摄影”和一个大概时间，很难说清。为每次请求生成不同编号，经过各边界时按约定传下去。查资料的人可以在收到报错时请小林提供页面上的简短参考号，去受控记录里找相关的处理过程。编号本身不应夹带邮箱，也不该成为别人凭它就能打开小林报名的方法。

有时只有一个地方没有记录。一笔请求在入口出现，应用没找到。先核对查的是哪套环境、哪个时间窗口，日志有没有抽样或写入延迟，再问是不是路由到了另一组实例。一早认定应用没收到，下午才想起自己看的只是其中一台，系统里再添一台机器，就足以让整个推理翻车。这里先带走那个便宜的动作：把自己的观察写成“我在这个地方找到了什么”，证据的范围会跟着句子一起清楚起来。

小林的请求已经找到收件人。接下来问一个还没法从 Network 面板上读出来的问题：若它只送回一对空方括号，小林该换个词，还是等学校把服务修好？
