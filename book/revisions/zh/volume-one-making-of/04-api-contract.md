# 没有找到课程，还是没有查到结果？

你想找一门讲 HTTP 的入门课程。在搜索框里输入关键词，选好“入门”，按下按钮。等了一会儿，页面告诉你：“没有找到课程。”

接下来，也许你会去掉筛选条件，把关键词缩短一点。再搜不到，就换个地方找。那句提示看起来只占一行，却已经替你安排了下一步。

但如果课程并不少，只是这次没有取得查询结果呢？用户可能认真修改了半天关键词，页面仍没有得到一份可以使用的答案。它十分客气，也十分稳定地把问题推给了搜索框。

我们用一个虚构课程网站看看这件事。这里只搜索一个较小的公开课程目录，不修改报名或其他业务记录；先假设一次只处理用户提交的一组搜索条件，没有分页或部分结果。

## 先说清在找什么

“搜索课程”听起来已经足够明确，动手写时，仍然会遇到一些小问题：关键词搜的是标题，还是连讲师简介一起搜？“入门”表示课程的分类，还是系统替每个人判断是否适合？没填写筛选条件，与填写了一个系统不认识的值，是不是同一回事？

这些决定未必复杂，但页面和服务端需要知道的是同一件事。这里把它们之间约定的请求入口、输入和返回结果叫作 API；而双方对这些内容的结构、含义与处理方式作出的约定，就是我们要讨论的接口契约。

对这个小例子，可以先约定：关键词按课程标题查找，去掉首尾空白后不能是空的；课程级别是额外的筛选条件。选“入门”，就只查目录中标为入门的课程。它不是对学习者的能力评估，也没有承诺每一门结果都适合你。两个条件同时生效，不是满足一个就可以。

请求可以写成这样：

```text
GET /api/courses?q=HTTP&level=intro
```

其中，`q` 放标题关键词，`level` 放级别。这个接口只接受 `intro` 和 `advanced` 两个级别值，分别表示入门和进阶；省略 `level`，表示不按级别筛选。传来一个不认识的值，服务端会说明参数不符合约定，而不是悄悄当作“全部级别”。否则，用户选着入门，页面却可能在展示另一个问题的答案。

这样，服务端拿到请求以后，就有了可以执行的意思：检查输入，按标题关键词和级别查询当前公开目录，再把结果整理成页面需要的格式。页面不必知道课程在数据库里分了几张表，但需要知道返回的东西该怎样使用。

如果请求带的是 `GET /api/courses?q=HTTP&level=expert`，它就过不了第一步。这个教学接口约定在查询前拒绝该请求，回复 HTTP `400`，响应体如下：

```json
{
  "error": {
    "code": "INVALID_LEVEL"
  }
}
```

页面可以保留关键词“HTTP”，并提示“请选择入门或进阶，也可以清除级别筛选”，让用户改好再搜。这里的 `400` 和错误标识是这个接口的约定。合法查询确实没有匹配项时，页面才报告没有结果。服务失败或没拿到可用回复时，页面说明这次未取得结果，不能据此要求用户修改筛选值。

## 返回的字段，要能接上页面的动作

假设这次正常查到了一门课程。我们约定成功搜索返回 HTTP `200`，响应体是这样的 JSON 数据：

```json
{
  "items": [
    {
      "id": "c-17",
      "title": "HTTP 入门"
    }
  ]
}
```

`items` 是本次查询的课程列表。在这个没有分页的小目录里，它包含符合当前条件的全部结果。每一项都要有非空字符串 `id` 和 `title`：前者表示是哪门课程，后者是展示给读者的标题。

这两个字段看着普通，却承担着不同的事。用户看到“HTTP 入门”，可以判断自己要不要进一步了解；页面则用课程标识关联后续入口，而不是把“列表里的第一项”当作课程身份。以后顺序变了，第一项可能已经换了课程。同样，只靠标题也不合适，课程不一定都起着互不相同的名字。

数据库里的列名也不必原封不动地交给浏览器。服务端可以把内部记录整理成这两个字段，再返回给页面。接口契约约定的是这一层交接，而不是要求数据库、服务端模块和页面组件使用同一种内部结构。

沿着一次正常搜索看，事情就接起来了：页面提出有含义的条件，服务端按约定查询并组织结果，页面再把结果表达出来。此时用户得到一张可以继续查看的课程卡片。它说明本次查询找到了这门公开课程，不表示用户已经报名、一定有名额，或这门课以后永远可用。那些是另外的产品约定。

## 结果为空，也是一种结果

再换一组条件，目录里确实没有匹配项。只要搜索按约定完成，服务端仍可以返回 `200`，只是列表变成了空数组：

```json
{
  "items": []
}
```

这时，“当前条件下没有找到课程”就有了依据。用户改关键词、放宽级别，都在回应刚得到的信息。这句话的范围也有限：它说的是当前公开目录中的这次查询，不是世界上没有这样的课程。

暂时无法完成查询，则是另一种情况。比如服务正在计划内维护，本例选择返回 HTTP `503`，并给出一个约定的错误标识：

```json
{
  "error": {
    "code": "SEARCH_UNAVAILABLE"
  }
}
```

`503 Service Unavailable` 可以表达服务因临时过载或计划维护而暂时无法处理请求；这里用的是维护这个设定。`SEARCH_UNAVAILABLE` 则是我们给应用起的错误名，不是所有 API 都认识的标准格式，也不承诺多久以后一定恢复。[RFC 9110 §15.6.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4)

这次页面应该表达“暂时无法完成搜索”，可以保留用户输入的条件。用户不需要为一次没有完成的查询反复修饰关键词。若决定暂时留下上一次的列表，也要说明那是先前结果，不能把旧答案当作这一次刚查到的内容。

一种很省事的写法，是在查询出错时返回空数组，让后面的显示逻辑继续走。眼前没有报错，页面也不用多画一种状态；但这同时把“没有匹配项”和“没有取得结果”合成了一句话。省下的分支，最后变成了用户多试几次的理由。

因此，空数组要保留它原来的含义。输入不合法，需要纠正参数；服务暂不可用，需要说明查询没完成；成功查询后确实为空，才显示没有匹配课程。代码里都可能暂时没有课程卡片，用户能据此作出的判断却不同。

## 能读成 JSON，还不够

页面真正处理回复时，还需要跨过几道小门槛。收到响应以后，先看它是否符合约定的成功状态，再读取并检查内容。使用浏览器的 `fetch()` 时，服务端返回错误状态也可能得到一个正常兑现的 `Response`；它不会因为收到了 HTTP 错误码，就自动把所有错误送进同一个异常分支。`Response.ok` 可以帮助判断状态是否在 `200` 到 `299` 之间，但仍不能代替本接口的结果约定。[MDN：检查响应状态](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch#checking_response_status)

接下来，`response.json()` 会把响应体按 JSON 解析。能解析，说明这一层语法读懂了；得到的值仍可能是数组、字符串、数字，或者一个与课程列表无关的对象。它不会顺便检查我们刚才约定的 `items`、`id` 和 `title`。[MDN：Response.json() 的返回值](https://developer.mozilla.org/en-US/docs/Web/API/Response/json#return_value)

对眼前这个接口，边界检查可以很小：成功结果应当是一个不是 `null` 的对象，而不是数组；`items` 必须是数组；每一项也要是对象，不能是 `null` 或数组，里面的 `id` 和 `title` 都是非空字符串。缺了 `items`，或者收到 `items: null`，都不能默认补成空数组，再宣布没有找到课程。标题意外成了数字，也应该被识别为回复不符合约定，而不是把这一项静悄悄地丢掉。

如果项目用 TypeScript，写一个结果类型很有帮助，它能让代码中的预期更清楚。但把读到的值写成 `as SearchResult`，不会增加上述运行时检查；类型断言在编译时会被移除。接收数据时是否执行了检查，仍要看实际代码。[TypeScript Handbook：Type Assertions](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions)

这些检查只回答了很小的问题：数据的结构和字段值，够不够按眼前的约定继续处理。标题即使是字符串，也可能写错；课程可能被错误分类；服务端也可能漏用了级别条件。检查字段不能证明这些事情正确，更不能替代访问权限判断。实现查询、整理响应和表达结果的各部分，仍有各自需要验证的责任。

错误回复也未必总有漂亮的 JSON。网络中断、代理返回了别的内容，或者错误体自身不符合约定时，页面仍需要一个说明“本次没有取得可用结果”的退路，不能因为读不出错误标识，又回到“没有找到课程”。这里先把这些结论分清，具体的异常捕获和恢复做法，后面再展开。

## 今晚才发现的旧页面

课程助教在办公室一直开着周三的页面，周五才按了一次搜索。新页面的开发者习惯先读取“总结果数”，没有就显示零。老接口恰好从没答应交这个字段，只答应成功时有 `items`。眼下返回的两条课都好好地坐在数组里，标题旁边却端端正正写着“找到了 0 门”。学员很有可能以为自己在看系统的幽默感。

先别急于在服务端永远加一个零。原先目录小，一次给全，拿数组长度确实可以数本次找到多少门。以后分页，眼前这两条只能说明本页有两条；若还想显示全库符合条件的数量，就得约定查询范围、权限过滤、计算时刻和是否精确。为了省一次昂贵的全量计数，也可以只告诉人家“还有下一页”。需求真正需要的是能往下翻，页面最初那个“共几门”也许只是设计稿恰好有地方写数字。

再让同事把其中一条课程的标题删掉。页面有两个选择：拒绝整份不合约定的答复，显示资料暂时不可用；或仅渲染有效的那条，诚实告诉读者有部分课程暂时无法显示，并记录具体的问题供维护者查。本例若必须保证“这是所有匹配课程”，静默过滤坏条目会损害这个承诺。判断依据不是同事喜不喜欢容错，而是学员是否会把残缺目录当成完整结果去做决定。

最后再看那两个同名标题。课程更名以后，旧链接仍可按编号去找；若课程确实下架，详情能说明目前不可读。反过来，把标题用作地址里的唯一钥匙，老师每改一个错别字，学生收藏夹里就可能多一个纪念品。这是在接口最小的时候值得留下的区别：有的字段给人阅读，有的字段让程序认出同一个对象。两者都写成字符串，类型声明只答了问题的一半。

## 把约定放回页面

最后可以回到最初的搜索框，看一看几种回答会把用户带到哪里：

| 这次取得的结果 | 页面可以怎样表达 |
| --- | --- |
| 成功搜索，列表里有课程 | 展示本次匹配课程，提供继续查看的入口 |
| 成功搜索，列表确实为空 | 说明当前条件下没有匹配项，允许修改条件 |
| 参数不符合约定 | 指出需要改正的条件，保留可继续编辑的内容 |
| 服务失败，或没有取得可用回复 | 说明本次没有取得可用的搜索结果，保留条件；不能断言没有课程 |
| 回复不符合约定的数据结构 | 说明暂时无法使用结果，不能当作有效空列表 |

把“没有找到课程”那一行单独拿出来，两边的同事现在可以问同一个问题：服务端是查完了交来一张空名单，还是查到一半没能交卷？只有前一种，才值得请那位学员再改一次关键词。
