# 最后一把椅子，两个人同时伸手

还剩一个位置。甲看见余量一，乙也看见一。甲写了一条报名，乙随后写了另一条。两人身份都合法，同一人也没有重复；可给他们准备的只有一把椅子。单人唯一约束挡不住这次超额。

一种设计是把扣减余量和创建报名放在同一数据库事务中。对同一场次做“仅当余量大于零才减一”的条件更新，检查实际更新行数；更新成功才写入有效报名，若写入因重复或其他原因失败就回滚整笔。以能对同一行更新正确串行协调的数据库为例，第一笔提交后，下一笔须对当前状态判断，或者收到冲突后重新开始判断。更新零行就不能照常确认报名。另一种方式是先锁住对应场次行，持锁者核对报名及余量、写完再释放；要约束所有能改名额的入口走同一规则。也可以用版本号条件更新检测有人抢先修改，冲突后重新读。

把刚才那一席再过一遍。假如甲扣了名额，写报名行却失败，整笔撤回，椅子还在。这叫原子性。乙同时来抢，得等甲办完再判断，或者遇到冲突重新读；两笔事务能看见彼此哪一步，由隔离规则决定。假如甲回滚后是乙拿到这一席并提交，系统重新启动，名单上仍应该能查到乙。这是持久性。

剩下那个 C，Consistency，讲的是提交前后都要满足已经定下的规则。比如甲不能在同一场有两条有效报名，数据库可以用唯一约束守住；但“扣一把椅子就要为一个人记上一笔”，需要业务代码把这两项放进同一事务，处理冲突和回滚。原子性、一致性、隔离性、持久性，按惯常顺序合写就是 ACID。

## 把两个时钟拨慢一些

若只有一台电脑，很难真的在同一毫秒按下两个按钮。在纸上用不着费这个劲。给甲、乙各一列，只允许自己一次往前写一行。先做一个确实会写坏的版本，两个人都凭刚刚读到的“剩一席”去保存报名。

| 先后 | 甲 | 乙 | 已提交的名单 |
| --- | --- | --- | --- |
| 一 | 读到余量一 |  | 空 |
| 二 |  | 也读到余量一 | 空 |
| 三 | 写入甲的报名，余量记零并提交 |  | 甲 |
| 四 |  | 按旧判断写入乙，余量也记零并提交 | 甲、乙 |

最后余量为零，看起来挺放心，名单却多了一位。保证余量字段永远不小于零，在这个错误版本里从头到尾都做到了。出错的是“已占用的席位加剩余席位要对得上这场容量”，这条关系跨了记录。查一个绿色数字，无法替另外两位证人免掉出庭。

再从一席重来。把“只有还有空位才扣一席”作为同一行上的条件写入，检查是否实际更新了一行，再在同一事务增加有效报名。轮到乙时，他可能要等甲提交，也可能得到冲突需重试；重试要重读，不能把自己几秒前看到的“一”带进下一轮。甲若已提交，乙不能再成功扣减。若甲因已有一条有效报名而在写入时报错，这一整笔撤回，乙才可能拿到那一席。两张表和规则站在一起，才看得出 A、C、I、D 这四个字母分别在保护哪种不走运。

有一个看起来更直观的做法：在进入办理前先给该场次加锁。持锁者查清是否已报、是否还有座位，完成必要写入就放锁。若所有改名额的入口都遵守它，老师后台代报名也很难插队；若有人写了一个“管理员快速加人”直接往名单里插一行，门口这把锁只管得住还愿意走门的人。写权限和业务校验要落在真正能改变记录的那些入口。

两种做法都会遇到拥挤。最后一席让所有人争同一行，给每个请求多开一个线程，可能只是让数据库同时看见更多等待者。别一边持有锁，一边去找远处的邮件服务问“可以替我寄确认吗”。一封邮件等三秒，就让后面所有报名的人一起陪了三秒。先把报名和要做的后续工作可靠记下，尽快结束事务；寄信是另一段要自己处理失败的路。这条路到第五部分再走。

## 把错放在不同的地方试一次

王老师请你验证班上不会超额。若只写两条成功报名的顺序测试，她得等到下一个抢座的星期一才知道中间有没有门缝。先把容量设为一，让两个独立的办理流程都走到想拿最后一席的位置，然后放它们继续。结果可能是甲成乙败，也可能反过来；真正要断言的是合格者中只有一个有效报名、余量为零，没人被告知一把不存在的椅子属于他。可重复的并发试验还要考虑死锁或重试上限，程序该给出能从记录中核对的最终结果。

第二次换成同一学员、同一场、两个窗口，班上有两席。两个请求同时到，理想结果仍只占一个位置。若第二个得知已存在，可以返回原报名而不是再扣一席。两位学员争一个名额和一位学员按两次用的是不同约束，两个实验都得保留。在代码里叫它们“重复报名测试一”和“重复报名测试二”，三个月后连写的人自己都得翻内容才知道在防什么。

第三次换成小林先取消、随后又想来。取消释放席位，历史上这位同学曾经占过座的那条记录仍可保留。用“一个人永远只能有一条报名”这种绝对约束，就会把改变主意当成系统错误。可以让有效状态下同一人同一场最多有一条，历史另外保存；也可以以一条当前记录加可追溯的变更描述过程。哪种适合，取决于是否需要说明昨天何时取消、今天为什么又在名单上。教室门口的老师只想知道现在该不该让他进来，接电话的教务同事也许还得知道为什么两封邮件说得不一样。

最后一组是断电。若业务记录和余量已经可靠提交，进程重启后还能查到同一个人；没提交的中间状态不能在名单里留下半条“既要来又不来”的记录。测试里要先写清是在提交之前关掉服务、提交之后丢掉回复，还是数据库本身发生了故障。把这三件事都叫“断网”，下次再争论应不应该自动重试，大家很可能各自都拿着一个正确答案。
