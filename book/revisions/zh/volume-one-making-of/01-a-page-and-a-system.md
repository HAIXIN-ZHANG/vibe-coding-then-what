# 一个页面，究竟连着什么？

课程列表已经显示出来了。搜索能用，按钮也能点。你选中一门课程，按下“报名”，页面弹出“报名成功”。看起来可以收工了。

这时，有人把页面关掉又打开，发现报名不见了。另一个人没看到成功提示，点了两次，结果报了两遍。还有人问：我明明没有这门课的访问权限，为什么改个地址就能看到资料？这些问题都出现在同一个页面上，原因却可能落在不同的地方。沿着这个功能走一遍，才知道该到哪里看。

本章使用一个虚构课程网站。假设它有浏览器页面、一个应用服务和一个业务数据库，报名记录由应用服务写入数据库。

## 从用户要完成的事开始

“做一个报名按钮”很容易理解，也很容易让人漏掉后面的半句话：用户按下它，是为了确认自己参加了课程，而且之后还能找回这条记录。

按钮是完成这件事的入口。颜色、文案、等待反馈很重要，但它们要与实际发生的事一致。

如果系统还没有确认报名结果，界面就直接显示成功，用户可能据此安排后续计划。如果报名已经完成，界面却只显示“出错了”，用户又可能重复操作。

把用户想得到的结果说清楚，就有了讨论各部分职责的依据。产品思维可以从这样具体的问题开始，不需要先写一大份产品文档。

先假设每门课这周只开一场，所以此处说“报这门课”，就能指明要去的那一场。以后同一门课开两个班，报名便要记清是哪一场。对这个例子，我们可以先约定：用户只能报名有权限参加的课程；同一用户在同一课程中只保留一条有效报名；完成后可以再次查询到记录。课程是否收费、能否候补、是否发邮件，暂时都不放进这一版。省掉这些需求，是为了看清眼前的事情。等条件改变时，再讨论需要增加什么。

周五下午，老师给这个愿望配了个更具体的时刻。她得在关门之前抄下明天要来的人，早晨照着摆椅子。小林则只想合上手机，跟家里说一声明早出门。我们可以请他们各做完自己的事，再看双方拿走了什么。

先让小林在家报上名。页面给他一条确认，编号叫 R17。让他把浏览器关掉，第二天重新登录，打开“我的报名”。如果先前的 R17 只存在按钮旁边那行字里，到了这一步，程序便要面对一个颇为朴素的困难：昨晚替它作证的那一页已经不在了。再请老师用自己的账号查同一场课。小林的页面不必向她开放，她的名单也不必交给小林。两边分别从获准看的记录中认出这次报名，这个约定才走完。

把一个条件拧一下。小林按下以后断网，R17 已经在老师的名单里，手机上却没有编号。第二天他还能从自己的身份和那场课找到记录吗？假如确认邮件也丢了，他需要的是另一个查找办法；重复收到三封确认邮件，他需要的依然只是一把椅子。我们不必第一天就设计完邮件系统，只需发现“记住那封邮件”不是这个承诺的好地基。

再请另一个没报名的同学照着打开课程。她应该能读到同一个课名，也应该能知道自己还没报上。若她的页面也写着 R17，我们刚才那次看似顺利的验收暴露了一个问题：程序可能把最后一张确认给了每个人。两个人、一门课，已经足够看出身份是这张图的一部分。

## 先画一张够用的图

一个带服务端数据的 Web 功能，可以先从请求与响应的关系理解：浏览器发出请求，服务端处理后返回结果，页面再表达它知道的情况。实际网站也可能在服务端生成 HTML，或经过缓存等中间环节；这里先聚焦页面已经打开之后的搜索和报名。

```text
浏览器中的页面
  │
  │ HTTP 请求：搜索课程 / 提交报名 / 查询自己的报名
  ▼
应用服务
  │  判断请求者可以做什么，执行报名规则
  │
  │ 数据库操作：查询课程 / 写入或读取报名
  ▼
业务数据库

结果沿相反方向返回：数据库 → 应用服务 → 浏览器页面。
```

这是一张简化的关系图。箭头表示本例中的调用方向，不表示机器数量，也不表示每个框都要单独拆成一个服务。

应用服务可以是一个普通应用里的若干模块。浏览器与服务端代码也可能放在同一个仓库，由同一个全栈框架组织。代码放在一起，并不会让它们运行在同一个环境中，也不会自动消除请求和权限边界。

顺着这张图，我们已经可以追问：报名记录在哪里，谁有资格改变它？暂时不加入缓存、队列或容器，也能先把这些关系看清楚。

## 边界：谁负责这件事？

这里说的边界，是责任和信任到哪里结束。它不只是文件夹之间的分隔线。

在本例中，页面负责收集用户选择、发起操作，并给出可以理解的反馈。应用服务负责确认身份与访问条件、执行报名规则。数据库保存记录，也可以通过约束帮助拒绝不合法的数据。

这几个部分不是各做各的。比如“不允许重复报名”，可以同时影响按钮反馈、服务端处理和数据库约束；但它们提供的保证并不相同。

按钮在请求期间禁用，可以减少用户误点，却不能阻止另一个浏览器窗口或直接发送的请求。真正决定是否接受报名的检查，需要在用户不能随意绕过的可信执行边界进行。

帮助用户正确操作，与保证规则无法被绕过，是相关但不同的责任。边界清楚之后，问题也能说得更具体：“按钮禁用漏了一个状态”，和“服务端允许重复写入”，需要不同的修正。权限、事务和约束的具体做法，我们稍后会继续讨论。

## 状态：我们在描述哪一份事实？

页面上的“报名成功”是一段文字。让它成立的，应该是已确认的业务结果。

如果只是把一个变量从 `false` 改成 `true`，页面可以立即变绿，但这不能说明报名已经被保存。

同一个功能里，会同时存在几种状态：

| 状态 | 本例中的含义 | 怎样得知 |
| --- | --- | --- |
| 页面输入 | 用户当前选中的课程 | 当前页面中的选择 |
| 请求进度 | 请求尚未发出、正在等待，或未取得结果 | 浏览器对这次请求的观察 |
| 业务记录 | 这个用户是否已报名这门课程 | 应用服务按权限查询数据库记录 |

这些状态有关联，却不能随意互相替代。页面选择了课程，不代表请求已经发出；请求已经发出，不代表报名已经完成；请求失败，也未必证明服务端没有完成报名。

其中最后一点值得多看一眼。

```text
先后顺序    浏览器                    应用服务与数据库

1           提交报名请求 ──────────→ 接收请求
2                                   完成检查，写入报名记录
3           未收到响应    ×──────── 返回成功结果，响应在途中丢失
4           等待结束，仍不知道结果   报名记录已经存在
```

图上只排了先后。走到第二步，名单里已经有了你；走到第四步，你自己还不知道。

此时，用户看见一个错误，后台却有一条有效记录。两边不一定有谁“撒谎”，它们拥有的信息不同。

我们可以给页面设计“暂时无法确认结果”的反馈，并提供查询报名状态的恢复路径。再次提交是否安全，还需要服务端的重复处理规则配合；恢复一个按钮，并不能替代这个设计。以后讲幂等和重试时，我们会回到这里。现在只需要看见：设计状态时，要说清状态属于什么、依据是什么，以及不知道结果时怎么办。

## 时间：先发生什么，用户要等到哪里？

结构图告诉我们有哪几个部分，但不会自动说明操作顺序。

在本例的正常路径里，我们希望先确认权限和报名规则，再保存记录，之后才返回足以确认结果的信息。页面根据结果表达成功，而不是点击后就直接报喜。

不过，“一次请求结束”也不总是代表全部工作结束。

假设以后增加“生成课程学习报告”，处理可能需要一些时间。产品可以先接受任务，让用户稍后查看结果。HTTP 中的 `202 Accepted` 就用于表达请求已接受处理、处理尚未完成；它本身不承诺最终一定成功。

我们不必在这里展开状态码。关键是双方对“完成”的约定：接到任务、开始工作、生成报告、通知用户，可以分别发生。

“已收到，正在生成”和“报告已生成”，不只是文案上的客气程度不同，它们表达的是不同时间点的事实。至于后续怎样查询、任务失败怎样恢复，需要另外设计，状态码不会替我们完成这些工作。

## 依赖：哪一部分停下，会影响谁？

一次报名需要等待数据库写入。如果数据库无法接受写入，本例中的服务就无法确认新的报名记录已经保存，页面也不能照常宣布成功。

这是一个必要依赖。把连线画出来，还要进一步问：调用失败、变慢或结果未知时，调用者怎么办？

再假设产品决定，报名成功后发一封提醒邮件。是否需要等邮件发送成功，才能把报名算作成功？答案取决于我们向用户作出的承诺，之后才是怎样实现的问题。

如果本例约定报名以已保存且有效的记录为准，邮件只是提醒，就可以让通知失败与报名结果分开表达，之后再处理通知。但如果用户必须通过邮件中的确认步骤才能取得名额，我们就引入了另一套业务状态，原来的约定需要改变。

把依赖移到后台，有时能让用户少等一段时间，同时也会留下任务记录、失败恢复和状态查询等工作。增加一个框，并不等于复杂度已经消失。

到这里，边界、状态、时间和依赖已经开始连起来了：谁接受操作，结果存在哪里，什么先发生，失败又会影响什么。

## 同一个功能，为什么有不同的合理方案？

只说“支持报名”，还不足以决定系统应该长什么样。

是一个小团队偶尔使用，还是某个时间集中开放？用户可以等待多久？访问条件会不会改变？记录需要保留多久？谁来维护和处理故障？

这些条件会影响方案。架构里的“取舍”，就是把它们放到一起，解释一个选择得到什么、付出什么。

| 可以提出的问题 | 它可能影响什么 |
| --- | --- |
| 哪些结果必须可靠，哪些可以稍后补上？ | 记录、通知、事务边界与恢复方式 |
| 用户需要多快知道结果？ | 等待反馈、超时约定、同步或后台处理 |
| 是否会出现大量同时操作？ | 共享数据竞争、容量、限流与负载验证 |
| 团队能维护多少运行组件？ | 部署方式、监控、故障处理和成本 |

表格里的关系是分析入口，不是固定答案。例如，“同时操作少”并不自动允许重复报名，“用户多”也不自动要求微服务。

这些问题里的“快”，也需要说得更具体。一次操作等了多久，是延迟问题；一段时间能完成多少工作，是吞吐问题；能否持续完成约定的任务，涉及可靠性。测量时需要说明对象、时间区间与负载，不能用一个“快”字代替。

对当前教学例子，我们先选择一个应用服务和一个业务数据库。这是为了让关系容易追踪，不是证明它适合所有规模的报名系统。后来需要改变设计时，也应该能指出新的条件或证据。

## 图应该帮我们回答问题

你刚刚已经用到了两种图：一张说明浏览器、服务和数据库的关系，另一张说明响应丢失时发生的顺序。

如果想进一步讨论报名状态，可以再画一个小图：

```text
提交前 ──用户提交──→ 等待结果
                         │
                         ├──确认有有效报名──→ 显示已报名
                         ├──本次提交未获接受→ 说明原因，结合当前报名状态处理
                         └──仍未确认状态────→ 提示待确认，提供查询方式
```

这张图描述的是页面的认知和反馈，不是数据库的全部业务状态。一次提交未获接受，不能直接翻译成“你没有报名”。比如第一次报名已经成功，只是响应丢失；再次提交时，服务端可能因已有记录而拒绝重复新增。用户此时实际已经报名。

页面应根据接口提供的可信当前状态显示已报名，或通过有权限的查询确认。只知道这次提交被拒绝、还不知道当前记录时，就说明原因并保留待确认状态。拒绝了一次动作，与当前有没有有效报名，需要分开看。

因此，同一个功能可以需要不同图：结构图看责任和连接，时序图看事件顺序，状态图看允许的变化。不用把所有信息都挤进一张图，也不需要每种图都画。[C4 的图示指南](https://c4model.com/diagrams)也有一个朴素的建议：先看图要讲给谁听，再选合适的层次。

读图时，可以先问：方框代表程序、数据还是部署位置？箭头表示调用、数据传递还是先后关系？这张图为了回答什么，省略了什么？

## 把这张图带进 AI 协作

现在再看“请帮我增加课程报名功能”这句话。

我们可以先补充少量会影响实现的条件，而不是把整本设计文档一起塞进去：

```text
目标：用户能为可参加的课程报名，离开页面后仍能查询结果。

现有约定：
- 报名资格由应用服务判断，页面显示用于引导。
- 同一用户在同一课程中只允许一条有效报名。
- 页面只在确认业务结果后显示已报名。
- 重复新增被拒绝时，区分本次动作与当前已有的报名状态。
- 未能确认结果时，提供查询状态的路径。

实现前需查看：现有课程权限、报名记录和请求错误处理的代码。
若缺少上述能力，先指出缺口，再讨论本次改动范围。

检查时区分：成功、无权报名、已有有效报名后再次提交、未能确认响应结果。
```

现在去看 AI 交回的代码。要是它只在浏览器里把按钮按灰，任务说明里那句“同一用户只允许一条有效报名”就还有一半没着落。带着这句约定往服务端走，才知道下一处该翻哪个文件。

## 再想一步：页面关掉之后呢？

如果用户提交报名后立即关掉页面，回来时我们应该显示什么？

仅记住“用户上次点过按钮”不够，因为操作可能被拒绝；仅记住“浏览器当时没收到结果”也不够，因为报名可能已经完成。

对于本章的设计，恢复页面时，应通过有权限的查询了解当前报名状态。查到有效记录，可以显示已报名；查询失败，就说明当前无法确认。

暂时没有查到记录，也不一定证明之前的提交已经失败。原请求可能还在处理：查询先返回暂无记录，报名随后才完成。即使查的是同一个数据库，也可能有这样的先后顺序。

如果接口能明确给出先前操作的最终结果，就按约定处理；若它仍可能在处理中，就保留待确认，不能仅凭这次空结果断言报名最终失败。没有未决操作时，普通查询当然仍可以按其约定展示当前未报名状态。

这个问题不要求立刻引入更多基础设施。它只是把最初那句“用户要完成报名”，补成了一个有边界、有依据、也能面对信息缺失的承诺。接下来，我们会先回到浏览器：用户看到页面、输入内容、点下按钮时，代码究竟在哪里运行，又怎样把数据变成界面。这张最小的系统图会留在旁边，帮助我们知道自己正在看哪一部分。
