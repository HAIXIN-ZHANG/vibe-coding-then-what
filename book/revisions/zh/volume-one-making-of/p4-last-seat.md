# 两个人、三份讲义，怎么数出了六个报名？

老师把周末班的名单递过来，上面明明只有两个人。后台课程摘要却端端正正写着“六人报名”。你数了一遍两个人，又数了一遍六，幸好还没来得及让朋友多搬四把椅子。

在这个虚构的小目录里，一门课有一个编号，一份报名把一位学员与一个开课场次连起来，讲义另有自己的编号和所属课程。课程标题可以相同，场次也可能改时间；拿标题和时间拼一个天然不会变化的名字，未免太信任教务处。这里选择稳定标识作关联，用外键约束引用确实存在的记录，用唯一约束保障同一场次同一人至多有一条当前有效报名。若还要保留取消和重新报名的历史，可以把历史另记或对有效记录设相应约束。这个规则跟“点了按钮就调用一次保存函数”相差好几步。

假如只为展示一张卡，也可以存一份课程文档，把课名和讲义清单嵌在一起，一次读取就凑齐了。若每个班都复制了同一本讲义的标题，更名就得找到每份副本；若只存讲义编号，改一处就行，展示时却得额外读取或在查询时关联。关系表也能把常用数据预先汇成一份，文档也可以引用另一份文档。两校的资料选哪种表示，都得守住各自的学校范围、同场余量和报名唯一性；把名单塞进一个大文档，并不会自动协调两个同时来报名的人。

## 一行究竟代表谁

假设今天只看同一所学校的一门课和它唯一的场次。两条有效报名，三份讲义。把课程同时和两张明细表连接，第一位学员会碰上三本讲义，第二位也一样。六行都是真的，每一行却是一对“报名加讲义”。这时数行数，查得再快，也赶不上老师的手指头。

若只要某场次的有效报名数，可以把问题缩回原来的粒度。下面的 SQL 只表达这项教学约定，命名参数由调用它的数据库驱动绑定：

```sql
SELECT COUNT(*) AS enrolled
FROM enrolments
WHERE school_id = :school
  AND session_id = :session
  AND status = 'active';
```

要在同一张课程卡上展示讲义数，可以先分别按课程或场次聚合到所需粒度，再连接两份小结果。还要保留零人报名的课时，从课程一侧做外连接，缺少匹配的报名字段会是 NULL。如果直接对连接后的行做 `COUNT(*)`，那一行保留下来的课也会被数进去；数非空的报名主键才会得到零。试着在纸上另放一张无人报名的课程卡，比盯着六行热闹的结果更容易发现这处差别。

ORM 能把这些关系映射成对象，读起来亲切。有时列表只取了二十门课，循环显示时每张卡又单发一条查人数的请求，于是变成一次加二十次。看数据库实际收到几次查询，再比较按这一页的场次集中查询。索引可以帮数据库缩小要找的行，是否用上、读了多少仍要看执行计划、数据分布和负载。连接池里的连接就那么多，几十条小查询也可能排出一条很长的队。

输入同样要按它的职务对待。学员搜索的标题当参数值传给查询；若页面给出“最新开课”选项，就把这个选项映射到应用事先写好的排序字段和方向，陌生选项交还给调用者纠正。排序规则属于查询结构，一段任意文字不能靠“绑定成一个值”就变成可信列名。以上查询里的学校参数也应来自服务已经核实的访问范围。数据库能忠实执行一份写错范围的查询，这恰是它有时令人担心的优点。

## 两张明细表约在了同一间教室

帮王老师做一张最朴素的表。把讲义名字写在三张卡上，叫 A、B、C。把小林、小周写在另外两张纸上。讲义属于课程，报名属于场次，这门课眼下只开了周六一场，所以我们特别容易误认为五张纸差不多都是一回事。在屏幕上看，反正也都挤在“周末摄影”这一栏底下。

| 学员报名 | 讲义 | 这行能回答什么 |
| --- | --- | --- |
| 小林周六场 | A | 小林所在的这场课配有 A |
| 小林周六场 | B | 小林所在的这场课配有 B |
| 小林周六场 | C | 小林所在的这场课配有 C |
| 小周周六场 | A | 小周所在的这场课配有 A |
| 小周周六场 | B | 小周所在的这场课配有 B |
| 小周周六场 | C | 小周所在的这场课配有 C |

六句每一句都是真的。“有六位学员”是哪一句说的？没有。若负责人要发一张清单告诉两位学员各读三本什么，这个结果刚好适用。若老师要搬椅子，只需那两张报名纸。很多写错的查询并不返回一张荒谬的表，只是把一个挺正确的答案递给了问另一件事的人。

来一条看似省事的修补：只数不同的学员编号。周六场会得到二。现在加开周日场，小林也单独报了周日，老师要看这个周末两场合计有多少个有效席位。小林占了两个席位，周六一把，周日一把。全课程按学员编号去重，却只肯给他算一位。问题变成“有多少不同的人来过这个周末的课”，这个答案又对了。拿 `DISTINCT` 覆住六个数字之前，不妨请王老师先把题目再念一遍。

小林报的是周日上午。老师另开了一个周日下午场，目前还没有人报名。把这个空场也放进摘要。先从所有场次出发，再去找各自的有效报名，找不到的也给这场留一行。若把“报名有效”这个条件最后才施在所有结果行上，可能连原本要保留的空场次也筛掉了。可以先在报名一侧筛出有效记录，再按场次归拢，最后把计数接回场次，没有匹配就显示零。这个零有可靠含义：在这次成功查询能看的范围里没找到有效记录。要是报名库没连上，课表还在，页面则该承认暂时查不到人数；拿一样的零补上，老师会欢欢喜喜把椅子搬走。

## 先问数据库到底替谁找东西

王老师进课程页面，首屏有二十个班，各自显示一行“已报名人数”。同事在应用里写了一个挺舒服的循环：先拿二十条课程，再打开每个对象的报名集合，让 ORM 代劳。浏览器只发出一次页面请求，负责数据库的同事却看见一串很相似的小查询。一加二十就是二十一，虽然在两人测试班里，它们都快得让人懒得数。

先保留相同条件，记录数据库实际收到的语句次数与等待，再换一种拿法。一次确定这一页有权看的场次，用这一组标识去报名表按场次聚合，将返回的场次编号映回卡片。有三个条件别在提速时省掉：学校范围、当前有效、缺少匹配也要保留原卡。原来二十次都正确，多合成一次以后把隔壁学校的人也算进来了，这不叫快，只能说走得很干脆。

若查询需要筛一所学校、一个场次和一种状态，相关索引有机会将要检查的记录缩在一块。但数据库也会考虑规模、分布与回表代价；测试库只有十几条，直接扫一遍完全说得过去。记录执行计划时顺带写下参数、匹配的行数、实际读了多少数据，以及当时还有几位老师正打开同一页。再往报名表加一个索引，写每条报名也得维护它，速度账不能只看读的一半。若王老师一天只开一次摘要，频繁变化的报名却有上万次，长久维护一份即时全校计数未必划算。

一个折中是先给大屏看几分钟前的汇总，旁边写清“更新至几点”；最后一个名额仍去权威业务记录办理。另一个折中是只集中查老师眼前这二十场，翻下一页再算下面的。两种都能给数据库喘气，只有第一种改变了时效承诺。老师在办公室准备周末大概需要的椅子，可以接受五分钟以前的数；小林点下最后一席时，一张越来越漂亮的旧报表帮不上忙。轮到他了。
