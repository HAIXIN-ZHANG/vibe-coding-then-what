# 新讲义上传到一半，旧的还能读吗？

周五的老讲义已经发给周末班。王老师发现集合点写错了，想用修订版盖过去。她最怕的是改到一半，旧的看不了，新的还没来。能不能先借个地方把这份文件放稳，再动全班桌上的那一份？

老师传来的文件太大，应用按已说明的大小限制拒收，这是它预期会发生的事，可以把限制直接告诉她。原件写到一半，存储突然不可用，就别请老师把文件名再改个漂亮点。先停止继续处理，释放打开的文件句柄，给本次临时对象做清理或留下可重试的清理记录。即使上层捕获错误并换成“暂时无法保存”，负责清理的那一层仍要在退出时执行自己的工作。原本已经生效的旧版讲义应继续可读，直到新版原件保存且发布条件满足。

处理响应时也有这个区别：浏览器收到一个 404 响应，与没能取得网络响应走的是不同的路。调用代码得检查状态，再读合适的内容。上层可以给用户适当的说法；内部保留足够的关联信息，别把原始凭证、存储路径或整份私密材料当错误详情送回页面。

## 先收原件，再把书架指过去

假设第一版的资料记录是 H1，指着一本可以完整读到的原件。老师传修订版，应用先给这次上传一个单独的位置 H2。此时学员页面仍沿有效版本看 H1。若把 H2 直接写进 H1 的位置，写了一半断开，两个原本清楚的东西都没了：旧文件已经损坏，新文件却还不齐。一份对外仍然可用的版本，至少值得花一个不同的名字。

上传完成，存储说对象已收到。应用可以按双方约定核对长度、校验值、格式和必要的可读条件，再在自己的业务库里记录“候选版本已就绪”。原件到了、预览未齐，是两份进度。若学校答应原件一到学生就能下载，可以先发布原件，预览一栏写“正在生成”。若学校不让人下载原件，只承诺阅读页面上的预览，则发布要等到能读的那一份确实到位。两种产品都可能合理，差的是门口什么时候挂上“欢迎进来”。

什么叫发布？在我们的例子里，是把课程资料的当前版本从 H1 指到已经验过的 H2，同时记录是哪位获准的老师作的决定。这样别人要么读到旧指针，要么读到新指针。对象存储和资料库通常不是一份本地事务里的两行，应用不能因为它先成功写过一个对象就宣布两个地方都已提交。若库写失败，已经落盘的 H2 暂时没有被选中，老师回来能查到这次尝试、按约定重试或让后台清掉孤立对象。此时继续读 H1 的人不必陪着程序一起猜。

反方向也做一次。库的指针改好了，老师的网页关掉，成功回执没有送到。她重新进来，看见当前版本确实是 H2，便可以停止折腾。若页面只记得“这一次上传按钮还在转”，老师很容易热心地再交一份 H3。给入口一个可查的操作编号和当前版本，既保护她的时间，也给后面处理过期预览的人留一个能说清先后的依据。

## 当天有两位老师都来改错

助教早上下载了 H1，下午王老师先发布 H2。助教沏了杯茶回来，把从 H1 改的文件也按下发布。他只改了一个错字，不知道王老师还换过集合点。若规则是后到的全部覆盖先到的，周六的学生又会走回旧门口。可以在发布时随请求带上“我是以 H1 为底改的”，提交前比较当前版本。若当前已是 H2，保住 H2，让助教看清变化再决定。对于一则公开的开课通知，宁愿多问一句，也值得让二十个人少跑一趟。

还可以换一个代价更小的场景：两位老师只是分别上传供自己挑选的私人草稿，两份都存下来，让他们之后任选其一发布，完全可以不用争同一个“当前”。冲突解决办法也要看共享的是哪个决定。把所有上传都串成一列，学校会为了两个人碰巧写了同名文件，让一百位互不相干的人一起等候。

王老师看着课程页打开新原件，稍稍放了心。可学员手里还有昨天的下载地址，搜索框里也仍能找到旧摘要。她不再签发旧版，已经拿到书的人手里却有不止一种“旧版”。
