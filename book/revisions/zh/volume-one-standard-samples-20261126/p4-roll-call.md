# 最后一把椅子，两个人同时伸手

还剩一个位置。甲看见余量一，乙也看见一。甲写了一条报名，乙随后写了另一条。两人身份都合法，同一人也没有重复；可给他们准备的只有一把椅子。单人唯一约束挡不住这次超额。

上一篇替老师数清了有效席位。这一次，名单正在被两个人同时改。把数据库里的“还有一个”读出来，只告诉我们刚才看见什么。要把这个位置交给谁，得看写入的那一刻还能不能办。

## 先把一把椅子摆进两张表

继续借这个虚构周末班，给例子定清条件。两所学校共用一个 PostgreSQL 数据库，本章按 PostgreSQL 18 的 Read Committed 隔离级别讲。报名与余量放在这个数据库里，所有报名、取消和教务代办都走同一套写入规则。当前场次容量固定。学校与学员身份已由服务端核实，写入参数来自获准操作的范围。下面两张表只负责把座位的账讲清楚，完整的账号、课程和授权表留在应用里。

```sql
CREATE TABLE sessions (
  school_id text NOT NULL,
  session_id text NOT NULL,
  capacity integer NOT NULL CHECK (capacity >= 0),
  remaining integer NOT NULL,
  PRIMARY KEY (school_id, session_id),
  CHECK (remaining >= 0 AND remaining <= capacity)
);

CREATE TABLE enrolments (
  enrolment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  school_id text NOT NULL,
  session_id text NOT NULL,
  learner_id text NOT NULL,
  status text NOT NULL CHECK (status IN ('active', 'cancelled')),
  FOREIGN KEY (school_id, session_id)
    REFERENCES sessions (school_id, session_id)
);

CREATE UNIQUE INDEX one_active_place_per_learner
  ON enrolments (school_id, session_id, learner_id)
  WHERE status = 'active';

INSERT INTO sessions VALUES ('school-a', 's-8', 1, 1);
```

第一张是场次表，`school-a` 是甲校的编号，`s-8` 是甲校周六场的编号。这一行的容量与余量都是一。第二张是报名表，目前为空。稍后用 `learner-a` 和 `learner-b` 区分学员甲和学员乙，两人报的都是甲校这一场；乙校另有自己的场次。报名编号由数据库生成。学校和场次一起作键，另一所学校碰巧也叫 `s-8`，不会领走甲校的椅子。外键要求每笔报名指向同校确实存在的场次。[PostgreSQL 约束说明](https://www.postgresql.org/docs/18/ddl-constraints.html)

把两张表的关系用文字排出来，是下面这个方向。每笔报名都指向一个确实存在的场次；一个场次可以还没有报名，也可以对应多条报名记录。

```text
enrolments（报名记录）
  (school_id, session_id)
            │ 同一对字段引用
            ▼
sessions（被引用的场次）
  (school_id, session_id)（联合主键）
  capacity / remaining
```

箭头表示外键引用。学校号和场次号要一起对上；它没有规定哪条 SQL 先执行，也没有替任何事务加锁。

最后那个索引只管有效报名。取消的历史还可以留在表里，同一个人同一场的有效记录最多一条。若把唯一性加在全部历史上，小林取消后再来，系统反倒会拿昨天的名字拦他。[PostgreSQL 部分索引](https://www.postgresql.org/docs/18/indexes-partial.html)

我们还要守住一条关系。每次事务提交后，同一学校同一场次的“剩余席位＋有效报名数”应等于容量。上面的范围检查可以挡住负余量，部分唯一索引可以挡住同人同时占两席。但这两张表之间的数量关系，还得由办理过程维护。

## 把两个时钟拨慢一些

给甲乙各一列，只允许自己一次往前写一行。先做一个确实会写坏的版本。

| 先后 | 甲 | 乙 | 已提交的余量与名单 |
| --- | --- | --- | --- |
| 一 | 读到余量一 | | 余量一，空名单 |
| 二 | | 也读到余量一 | 余量一，空名单 |
| 三 | 写甲的报名，余量直接设零，提交 | | 余量零，甲 |
| 四 | | 凭旧判断写乙，余量也设零，提交 | 余量零，甲、乙 |

从头到尾，余量都没有小于零，学员也没有重复。错的是最后那笔加法：零加二，竟等于容量一。查一个绿色数字，无法替另外两位证人免掉出庭。

这次让数据库在修改场次行时自己检查余量。下面是应用送到数据库的一段 SQL。甲乙的请求都把 `$1` 绑定为 `school-a`，把 `$2` 绑定为 `s-8`，因此争的是同一行。条件命中才扣一，`RETURNING` 把改过的行交回来。应用必须看有没有这一行。

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;

UPDATE sessions
SET remaining = remaining - 1
WHERE school_id = $1 AND session_id = $2
  AND remaining > 0
RETURNING remaining;
```

先停在这里。甲执行完，自己能看见余量零，但还没提交。乙对同一行执行这条更新，要等甲结束。若甲提交，乙会对已更新的行重新判断条件，零已经不满足“大于零”，于是乙没有更新任何行。这里用到的是这一隔离级别下对同一行更新的处理，不能从它推导出所有复杂查询都能这样协调。[PostgreSQL Read Committed](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)

甲拿到一行返回后，继续在同一个事务里写报名。INSERT 的 `$1`、`$2` 仍绑定刚才的学校与场次，`$3` 绑定获准报名的学员号：甲用 `learner-a`，乙轮到能办理的分支时用 `learner-b`。

```sql
INSERT INTO enrolments (school_id, session_id, learner_id, status)
VALUES ($1, $2, $3, 'active')
RETURNING enrolment_id;

COMMIT;
```

只有更新成功的分支才能走到这两句。如果 INSERT 报错，应用应执行 `ROLLBACK`，把先前扣掉的一席一起撤回。这些是由应用绑定参数、按返回行数选择的片段，不能把几个代码块依次贴进去无条件执行。可以照着下面的控制流程，把两个分支补在调用处。

```text
开始事务
尝试条件扣一席
  返回一行 → 尝试写入有效报名
                写入完成 → 提交成功后交回报名编号
                写入异常 → 回滚整笔事务
  返回零行 → 回滚，结束本次办理
约束冲突或零行之后，需要解释当前状态时：
  另开只读事务，从权威记录查询当前报名与场次
  读取结束后提交这个只读事务
```

甲要是写报名失败，就在表里填“回滚”。此时乙等来的重新判断又有一席，可以继续写自己的报名。甲乙两条时间线最后只会给一人留下有效座位。

```text
甲  条件更新一行 ─ 写报名 ─ 提交
乙        尝试更新 ─ 等待 ─ 条件不再满足 ─ 零行 ─ 回滚

甲  条件更新一行 ─ 写报名报错 ─ 回滚
乙        尝试更新 ─ 等待 ─ 仍有一席 ─ 写报名 ─ 提交
```

第一种安排结束后，`sessions` 里 `school-a / s-8` 的余量是零，`enrolments` 里留下的是同一学校、同一场次下 `learner-a` 的 active 记录；第二种同样余量为零，留下的则是 `learner-b`。被回滚的那笔既不留有效报名，也不单独扣走一席。

图里的箭头只表示这两种安排的先后，等待没有固定时长。若数据库检测到死锁，或操作遇到锁等待超时，失败的办理也要先结束、回滚。可重试的错误从整笔事务开头重新判断，限制次数并留出间隔。反复沿用先前读出的“一”，给它重试一百遍也不会更接近现在。各个入口保持相同加锁顺序，可以减少互相等住的机会。[PostgreSQL 锁与死锁](https://www.postgresql.org/docs/18/explicit-locking.html)

## 更新零行，门口站着的可能已经报过名

甲已经拿走最后一席，手机没收到回复，又按了一次。这次条件更新返回零行。如果应用立刻说“满了，你没报上”，甲手里的两次操作就给了他两个相反的人生建议。

先执行 `ROLLBACK` 结束这次更新事务。再从权威库开一个新的只读事务，用同一条查询取得该场次与本人当前有效报名。下面的表名、编号沿用前文，先核准身份再绑定参数。

```sql
BEGIN ISOLATION LEVEL READ COMMITTED READ ONLY;

SELECT s.remaining, e.enrolment_id
FROM sessions AS s
LEFT JOIN enrolments AS e
  ON e.school_id = s.school_id
 AND e.session_id = s.session_id
 AND e.learner_id = $3
 AND e.status = 'active'
WHERE s.school_id = $1 AND s.session_id = $2;

COMMIT;
```

这是一次查询看到的当前状态。若其他人紧接着取消，它返回后就可能又变。页面可以把这个时点交代清楚，想继续办理仍得重新走条件写入。

| 读回结果 | 这次可以告诉学员什么 | 还有哪件事没有查明 |
| --- | --- | --- |
| 有本人有效报名编号 | 查询时你已在本场名单里 | 它是否来自刚才那次请求 |
| 无本人有效报名，余量零 | 查询时名单里没有你，本场已满 | 旧请求是否曾办成后又被取消 |
| 无本人有效报名，余量大于零 | 查询时还有余位，本次未新增 | 后续确认能否取得这一席 |
| 查不到场次行 | 本范围内未找到这个场次 | 是否场次撤销、参数或可访问范围有变化 |
| 查询失败或结果未知 | 暂时无法核对，请保留原操作信息 | 当前状态和旧请求结果 |

另一种重复也值得单独走。把初始容量改成二，同一个学员开两扇窗口。第一笔扣一并提交，第二笔仍能扣一，但 INSERT 遇到有效报名的唯一冲突。第二笔必须先回滚，再开启上面的只读事务查询。最终只占一席，余量仍为一。若异常以后继续在已失败事务里查名单，或者捕获错误就顺手保留那次扣减，老师会得到一把没人来坐的椅子。

新查询只能回答当前状态。假如甲原来报成，后来已取消，如今查不到有效报名，就不能因此宣布原来的提交从没成功。提交回复丢失时，要查“那一次到底办没办成”，仍需要稳定的操作身份与终局记录。第五部分会接着讲那张回执。这里的报名编号标识一条报名，尚未替每次请求记完整历史。

## 取消一次，椅子回来几次

甲要退出，先核身份和他准备取消的报名编号。服务端知道这条报名属于哪个学校、场次，再按“先场次行，后报名行”的顺序办理。所有入口都遵守这个顺序。别让报名的人拿着场次等名单，取消的人拿着名单等场次，最后请数据库来劝架。

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;

SELECT session_id FROM sessions
WHERE school_id = $1 AND session_id = $2
FOR UPDATE;

UPDATE enrolments SET status = 'cancelled'
WHERE school_id = $1 AND session_id = $2
  AND learner_id = $3 AND enrolment_id = $4
  AND status = 'active'
RETURNING enrolment_id;
```

`$4` 是本人确认要取消的那条报名编号。场次查不到就回滚并结束。锁到场次以后，再看第二句有没有改到一条有效报名。返回一行，才继续下面这一步；返回零行就结束这笔事务，本例统一 `ROLLBACK`，不给余量加数。

```sql
UPDATE sessions SET remaining = remaining + 1
WHERE school_id = $1 AND session_id = $2;

COMMIT;
```

加回余量也必须更新一行，任何异常都撤回整笔。第一次取消把状态从 active 改成 cancelled，再加回一席。第二次带着同一个报名编号来，条件已不满足，改动零行，余量保持原样。如果这个人后来明确决定再报，新的有效报名有新的编号；迟到的旧取消还指向旧编号，不能取消他今天的新决定。取消重发一次就凭空多出一席，老师下次就得向家具店解释这套业务了。

| 同一场的动作 | 初始余量／有效人数 | 提交后的余量／有效人数 |
| --- | --- | --- |
| 两人争一席，只有甲办成 | 1／0 | 0／1 |
| 甲已占最后一席，再到一次 | 0／1 | 0／1 |
| 容量二，同人两窗口 | 2／0 | 1／1 |
| 取消甲的有效报名一次 | 0／1 | 1／0 |
| 同一报名再取消一次 | 1／0 | 1／0 |

每行是独立设定，初始状态按该行重置。余量与有效人数相加，始终回到这一行的容量。

## 那四个字母保护了哪一种不走运

甲扣了名额却没写成报名，回滚让椅子回来，这是原子性。我们规定提交前后都要满足座位与名单的关系，这是一致性。唯一索引、外键和检查约束维护各自能表达的规则，跨表加法由事务中的业务过程共同维护。老师后台若绕过它直接插一笔报名，声明式约束也未必能发现超额。

乙等甲结束以后再判断，涉及隔离。本章已经把用到的数据库与隔离条件摆在桌上。乙最终提交了，系统重启后还应能从持久记录找到他，涉及持久性。恢复能力也要核实际数据库配置、存储和故障范围，应用进程重启通过一遍，不能证明各种数据库故障都恢复过。原子性、一致性、隔离性、持久性，惯常合写为 ACID。

验证时可以让两条独立连接停在抢同一行之前，分别放行，再核余量和名单；让第一笔在写报名前故意回滚，再看第二笔接住哪一席。本章表格是依据上述条件的纸上推演，尚未在 PostgreSQL 上完成双连接实跑。读者实跑时应记录数据库版本、隔离设置和提交结果。还可以把故障放在提交之前、提交之后丢回复、数据库本身故障三个位置。把它们都叫“断网”，下次讨论该不该重试，大家可能各自拿着一个正确答案。

别一边持有场次锁，一边找远处的邮件服务问“可以替我寄确认吗”。一封邮件等三秒，后面的报名也跟着陪三秒。把必要的业务记录及可靠的后续工作交代好，尽快结束事务，寄信的失败另有一段路要走。

老师现在可以按有效名单摆椅子。可是甲手里还留着上次报名时的课程名，教务刚把课名改了。今天的名单与昨天的确认单各该显示哪句话？下一篇轮到这些记录该由谁改。
